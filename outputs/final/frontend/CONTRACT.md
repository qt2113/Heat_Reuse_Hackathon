# Site 1 frontend data contract (v1)

All files are generated by `python -m model.run_final_analysis --stage frontend` from validated Model A/B/C outputs.
The map should treat the files as read-only and must not hardcode any number shown to users.
`contract_validation.csv` (FE1–FE5) checks this bundle.

## Files

| File | Use in the map | Size |
|---|---|---|
| `candidates.geojson` | Building layer: source, shortlisted, eligible-not-shortlisted, excluded (with reason) | 0.4 MB |
| `configurations.json` | All 1,536 enumerated networks with indicators, dimension scores and feasibility | 2.1 MB |
| `indicators.json` | The 13 indicators: id, dimension key (T/E/N/S), name, unit, direction, formula | 3 kB |
| `recommendations.json` | Model C picks per weight preset, with generated explanations for selected and excluded buildings | 39 kB |
| `allocation_today.json`, `allocation_post_rebuild.json` | Seasonal heat allocation of the equal-weights recommendation | 61 kB each |
| `portfolios.json` | The four compared proposals (cards): buildings, architecture, outcomes, monthly matching, break-even, governance | 68 kB |

## Keys and units
- **`property_id`** is the LL84 property ID, used as a string everywhere.
- **Rebuilt sites** appear in `members` as `rebuild:<anchor property_id>` (`rebuild:2831044` = Rebuilt Fulton, `rebuild:4473909` = Rebuilt Elliott-Chelsea).
  - Draw them at the anchor feature's coordinates.
  - Label them as future buildings with modelled demand (assumptions A03, A19).
- **Units:**
  - energy: MWh/yr
  - money: USD2025/yr (negative `E_val` = additional cost vs today)
  - CO₂: tCO2e/yr (LL97 factors)
  - percentages: 0–100
- **`horizon`** is `today` or `post_rebuild`. The two horizons cannot coexist physically, so show them as a toggle, never mixed.

## `configurations.json` record
```
config_id, horizon, n_buildings, members[], feasibility, failed_checks[], tech_ok,
T_cov, T_lf, T_bk, E_lcoh, E_val, E_fund, N_co2, N_erf, N_gas, S_li, S_aff, S_eq, S_fac,   // raw indicators (units in indicators.json)
n_<indicator>                                   // 0-1 normalised, already direction-corrected (1 = better)
score_T, score_E, score_N, score_S              // dimension scores = mean of that dimension's n_ values
pareto, Q_DC_used_MWh (heat reused), Q_network_MWh (heat delivered), capex_total, route_m,
f1_carbon_price_to_close, overall_equal_weights
```

## Rules the map must implement
1. **Weights.** There are four sliders: Technical, Economic + Delivery, Environmental, Social + Regenerative.
   - They must sum to 100%; reject or renormalise otherwise.
   - Equal weights are only the demonstration default, and the UI should say so.
2. **Score.** `overall = wT·score_T + wE·score_E + wN·score_N + wS·score_S`. Compare scores within a horizon only.
3. **Recommendation** (the reference implementation is `_js_choose` in `model/run_final_analysis.py`):
   - Use only networks with `n_buildings > 0`.
   - If any is `fully_feasible`, pick the best-scoring one.
   - Otherwise pick the best-scoring `conditionally_feasible` one, and show exactly this message: **"No fully feasible configuration under the current assumptions."**
   - Never recommend an `infeasible` one.
   - For every configuration today, the message must be shown.
4. **Weights re-rank, they don't change results.** A weight change must never change any KPI of a configuration; only the ranking changes.
5. **Keep scores and outcomes apart.** Always show the measurable outcomes next to the score: `Q_DC_used_MWh`, `E_val`, `N_co2`, `S_li`, `S_fac`, `E_fund`.
6. **Governance items are unscored.** The `portfolios.json → _governance` items carry an evidence level. Show them as panels and never convert them into points.

## Explanations
`recommendations.json[horizon]["explanation_equal_weights"]` holds:
- `selected[]`: facts, reasons and limitations for each chosen building, from leave-one-out comparisons;
- `not_selected[]`: reasons for each excluded building (temperature incompatibility, connection cost, value, feasibility, score).

For other weights, show the incremental values (`delta` between the chosen network and the network with or without the building), computed from `configurations.json`.

## Seasonal allocation (`allocation_*.json`)
- **`monthly_system`:** `dc_heat_available_MWh[12]`, `dc_heat_used_MWh[12]`, `demand_MWh[12]`.
- **`weeks`:** `coldest_week`, `april_week` and `july_week`, each with hourly `T_out_C`, `dc_heat_available_MW`, `dc_heat_used_MW` and `demand_MW` (168 values).
- **`buildings[]`:** `monthly_network_MWh[12]`, `monthly_backup_MWh[12]`, `monthly_loop_heat_MWh[12]`, hourly `weeks`, and `merit_rank` (1 = served first when heat is scarce).

## Portfolios (`portfolios.json`)
The keys are `minimum_cost`, `minimum_cost_network`, `proposal_phase1`, `proposal_phase2`, `proposal_phase2_school`, `balanced`, `balanced_today` and `community`. Each has:
- `buildings[]`: scope served, heat, peak, heat-pump size, summer/winter ratio, backup, bill change, monthly heat;
- `architecture`;
- `outcomes`: heat reused/delivered, ERF, net value, CO₂, households, facilities, funding need, actor positions, feasibility;
- `matching`: monthly supply vs demand;
- `break_even`: carbon, electricity, gas and steam price, and capital-grant share needed.

## Caveats to display
- Every network loses money under current assumptions, and every recommendation carries the no-feasible message.
- Scores are relative to the enumerated set (min-max per horizon); outcomes are absolute.
- After the rebuild, the NYCHA affordability indicator (S_aff) is the same for every network (Term 4 cap), so it does not move the Social score.
